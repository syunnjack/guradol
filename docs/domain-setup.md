# ドメインを設定する手順

**この順番を守る。飛ばさない。設定したら触らない。**

2026年9月に guradol.jp で失敗した。証明書が発行されないので、カスタムドメインの
再設定・解除・Pages の再作成を5回以上繰り返した。GitHub は設定を変えるたびに
「このドメインは追加されたばかりです」の状態へ戻すため、**発行処理が毎回
振り出しに戻っていた。** さらに cname を空にする API を投げて Pages サイトごと
消し、本番を10分落とした。3日かけて開通しなかった。

原因は待てなかったことで、設定内容ではない。DNS も Pages の設定も、
最初から稼働中の他サイトと同一だった。

---

## 手順

### 1. DNS を向ける（レジストラ側）

ドメインの A レコードを、GitHub Pages の4つに設定する。

```
A  @  185.199.108.153
A  @  185.199.109.153
A  @  185.199.110.153
A  @  185.199.111.153
```

`www` の CNAME は任意。付けるなら `<ユーザー名>.github.io`。
**これは阻害要因ではない。**稼働中の darekore.jp と midnightpit.jp も同じ設定で
動いている。guradol.jp のときに「www を消してください」と3回依頼したのは、
私の誤った推測だった。

### 2. 反映を待つ

```bash
python scripts/check-domain.py <ドメイン>
```

`GitHub Pages を向いている` と出るまで待つ。**反映前に Pages を設定しない。**

ネームサーバーごと移設した場合、レジストリ側の委任変更なので数時間かかる。
移設中に古いゾーンを見ても永遠に変わらない。権威サーバーが変わったかを見ること。

### 3. ビルドのドメインを変える

`scripts/build-site.mjs` の `SITE_DOMAIN` だけを変える。
CNAME・canonical・サイトマップ・llms.txt・OGP・構造化データ・連絡先メールは
すべてここから作られるので、個別に書き換えない。

環境変数でも指定できる。

```bash
SITE_DOMAIN=example.jp node scripts/build-site.mjs
```

### 4. デプロイする

`main` に push すれば `deploy.yml` が走る。`dist/CNAME` が出るので、
デプロイのたびにカスタムドメインが再適用される。

### 5. GitHub の Settings → Pages でカスタムドメインを設定する

**Web UI から行う。API は使わない。**

`PUT /repos/.../pages -f cname=""` は Pages サイトごと消す。2026年9月2日に
これで本番を落とした。解除が必要なときも Web UI から行う。

### 6. 待つ。触らない。

証明書は `new`（発行待ち）から始まる。touge-start.jp は DNS が正しく向いてから
**2分**で `approved` になった。

**24時間は何もしない。**この間に設定を変えると振り出しに戻る。
状態を見るのは `check-domain.py` だけにする。これは読むだけで何も変えない。

### 7. HTTPS を有効にする

証明書が `approved` になったら、Settings → Pages の **Enforce HTTPS** を有効にする。

### 8. Search Console

所有権確認のタグは `build-site.mjs` の `SITE_VERIFICATION` にある。
ドメインを変えたら、新しいプロパティで発行し直して差し替える。

**サイトマップの送信は HTTPS が開通してから。**サイトマップ内の9,760件はすべて
`https://` で書かれているため、開通前に送ると全件が取得エラーになる。

---

## やってはいけないこと

- 証明書の発行待ちに、カスタムドメインを設定し直す
- `cname=""` を API で投げる
- 発行待ちの原因を推測して、正しく設定されている DNS レコードを消させる
- 「実害はほとんどない」と言って HTTP のまま放置する。ブラウザは
  「保護されていない通信」と表示し、検索評価にも影響する
